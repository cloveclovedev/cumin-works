定期確認

cuminがGitHubをいつ、どの順に読み、どう次のアクションを決めるかを決める。状態ごとのアクションは各カテゴリのページで、Agent起動を止める条件は利用制限とAgentのCWK-AGENT-018で決める。

全体像

1つのリポジトリの1回の定期確認の流れを示す。

図の元ファイル: overview.puml

overview.puml

作業の状態は、すべてGitHubにある。cuminが手元に持つのは、失っても作業を失わないものだけである。そのため、cuminを止めても再起動しても、次の定期確認がGitHubの事実から続きを決める。

要件

決め方

CWK-POLL-001 閉じた要求Issueには何もしない

cuminは、閉じた要求Issueを読まず、ラベルを替えず、コメントも書かない。

  • 検証: test 閉じた要求Issueに、cuminはGitHubへの書き込みをしない

CWK-POLL-002 事実から決める

cuminは、GitHubの事実と、Agentが動いているか（CWK-AGENT-001）だけで、次のアクションを決める。同じ事実からは、いつも同じアクションを決める。決めるのは、定期確認のときと、Agentの実行が終わった直後で、どちらも同じ決め方をする。

  • 検証: test 実行が終わった直後にGitHubを読めなかったときも、次の定期確認で、読めたときと同じアクションになる

CWK-POLL-003 手元に持つもの

cuminがHostの手元に持つのは、失っても作業を失わないものだけである。Agentのセッションの番号、チェックの修正を頼んだ回数、使用率とリセット時刻、5時間制限を使い切る許可、ツール動作確認の結果、止める予約、やり直しの回数、通知を送った記録がこれに当たる。レビューのラウンドの数は手元に持たず、Pull Requestのレビューから読む。

  • 検証: test 手元の状態をすべて消してcuminを再起動しても、作業中のIssueが続きから進み、同じAgent起動が二重に起きない。Maintainerがcumin/status/readyを付け直す必要はない

間隔

CWK-POLL-004 定期確認の間隔

cuminは、作業中のリポジトリをpoll_interval（初期値は60秒）ごとに、作業中でないリポジトリをidle_poll_interval（初期値は5分）ごとに確かめる。作業中とは、次のどれかが成り立つことである。

  • そのリポジトリでAgentが動いている
  • 状態がready、planning、acceptingの要求Issueがある
  • 状態がready、implementing、checking、reviewing、mergingの実装Issueがある
  • 前回の定期確認で、アクションをしたか、失敗した

awaiting-で始まる状態のIssueしかないリポジトリは、作業中でない。そのため、Maintainerの操作にはidle_poll_intervalのうちに気付く。

  • 検証: test 作業中のリポジトリと作業中でないリポジトリを同時に扱うと、それぞれの間隔で確かめる。作業中でないリポジトリでMaintainerがcumin/status/readyを付けると、idle_poll_intervalのうちに着手する

着手

CWK-POLL-005 同時に進めるIssueの数

1つのリポジトリで同時に進めるIssueの数は、max_issues_in_progress（初期値は1）までである。含めるのは、状態がplanning、acceptingの要求Issueと、implementing、checking、reviewing、mergingの開いている実装Issueである。implementingの要求Issue、readyのIssue、awaiting-で始まる状態のIssueは含めない。違うリポジトリのIssueは、並行して進めてよい。

  • 検証: test max_issues_in_progressが1のリポジトリで、implementingの実装Issueがある間は、別のreadyの実装Issueに着手しない。awaiting-blocker-mergeの実装Issueしかなければ着手する

CWK-POLL-006 着手の順番

空きより多くのIssueに着手できるとき、cuminは優先度の高い順に着手する。同じ優先度なら、Issueの番号の小さい順である。

  • 優先度のラベル（ラベルのCWK-LABEL-008）のないIssueは、ラベルのあるIssueのあとに着手する

  • 優先度のラベルのない実装Issueは、その要求Issueの優先度を使う

  • 優先度のラベルが2つ以上付いたIssueは、高いほうを使う

  • 優先度は、着手できるIssueの間の順番だけを決める。blocked byのIssue、同時に進めるIssueの数、利用制限を越えて着手することはなく、動いているAgentを止めることもない。

  • 検証: test 番号の大きいIssueに高い優先度のラベルがあると、そちらから着手する。同じ優先度なら番号の小さい順、ラベルのないIssueは最後である

  • 検証: test 要求Issueだけに優先度のラベルがあると、その実装Issueはその優先度で着手される

GitHubの呼び出しの失敗

CWK-POLL-007 一時的な失敗のやり直し

一時的な失敗は、ネットワークの誤り、5xxの応答、二次のレート制限、一次のレート制限を使い切ったことの4つである。ネットワークの誤りと5xxの応答は、読み取りに限り、数秒あけて3回までやり直す。書き込みはやり直さない。答えが届かなかった書き込みを、二重にしないためである。

  • 検証: test 読み取りが1回だけネットワークの誤りで失敗しても、やり直しで成功し、そのまま進む
  • 検証: test 書き込みが5xxで失敗しても、やり直さない

CWK-POLL-008 レート制限

レート制限に当たると、cuminはGitHubが返す時刻まで、そのGitHub AppのインストールでGitHubを呼ばない。一次のレート制限はリセットの時刻まで、二次のレート制限はretry-afterの分、なければ1分待つ。呼び出しの中では待たず、その時刻のあとの定期確認でやり直す。待つ間も、ほかのリポジトリは進める。

  • 検証: test 一次のレート制限を使い切ると、リセットの時刻までGitHubを呼ばず、そのあとの定期確認で続きから進む

CWK-POLL-009 失敗のあとは何も持たない

やり直しても一時的な失敗で終わったとき、cuminは何も持っておかない。Issueは今の状態のまま残り、次の定期確認が同じ事実から同じアクションを決める。すでに済んだ書き込みは読み直しで見えるので、二重にはしない。

  • 検証: test Agentの実行のあとで読み取りが失敗し続けても、Issueはラベルを保ち、あとの定期確認で、失敗しなかったときと同じアクションをする。書き込みは二重にならない

CWK-POLL-010 続けて失敗したら知らせる

同じリポジトリの定期確認が、同じ理由で3回続けて失敗したら、cuminは通知する。次に知らせるのは、その間に定期確認が成功したあとである。一次のレート制限を使い切ったことも、この通知で分かる。

  • 検証: test 同じ理由で5回続けて失敗しても、通知は1回だけである。成功したあとに、また3回続けて失敗すると、もう一度通知する

全部を読めないIssue

CWK-POLL-011 読む数の上限

cuminは、1つのIssueについて読む数に上限を持つ。sub-issueは12件ずつ、3ページの36件までを読む。sub-issueが36件を超えたIssueは、全部を読めないIssueである。ラベル、blocked byのIssue、結び付いたPull Requestがcuminの読む数を超えたIssueも、同じである。sub-issueの1つが全部を読めないIssueなら、その要求Issueも全部を読めないIssueとする。

  • 検証: test 閉じたものを含めてsub-issueが20件ある要求Issueは、全部を読み、今までどおり進む
  • 検証: test sub-issueが37件ある要求Issueは、全部を読めないIssueになる

CWK-POLL-012 全部を読めないIssueには何もしない

全部を読めないIssueには、cuminは何もせず、ラベルも替えない。ほかのIssueは今までどおり進める。cuminは、Issueと超えた上限を書いて、1回だけ通知する。次に知らせるのは、そのIssueを全部読めたあとである。

  • 検証: test 全部を読めない要求Issueと、別のreadyの実装Issueがあると、別の実装Issueには着手し、全部を読めない要求Issueとそのsub-issueには何もしない
  • 検証: test 全部を読めないIssueがあるまま定期確認を3回行っても、通知は1回だけである。sub-issueを36件以下に減らすと、次の定期確認から今までどおり進む

受け入れテスト

# 場面 期待する結果
1 readyの実装Issueを1つ置き、定期確認を2回以上またぐ Implementerの起動は1回だけである（CWK-POLL-002、CWK-AGENT-002）
2 cuminを止めて、手元の状態を消し、起動し直す GitHubを読み直して、続きから進む。同じAgent起動は二重に起きない（CWK-POLL-003）
3 着手できるIssueが2つあり、番号の大きいほうに高い優先度のラベルがある 優先度の高いほうから着手する（CWK-POLL-006）
4 Agentの実行のあとで、GitHubの読み取りがやり直しても失敗する Issueはラベルを保ち、あとの定期確認で同じアクションをする（CWK-POLL-007、CWK-POLL-009）
5 sub-issueが36件を超える要求Issueがある その要求Issueには何もせず、通知が1回届く。ほかのIssueは進む（CWK-POLL-011、CWK-POLL-012）

範囲外

  • 同じリポジトリを、2つのcuminで同時に扱うこと。Agentが動いているか（CWK-AGENT-001）は、1つのcuminの中の事実である。
