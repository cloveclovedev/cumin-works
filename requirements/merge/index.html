マージ

Reviewerが承認したPull Requestをマージし、実装Issueを閉じるまでの流れを決める。マージ判断、マージ、実装Issueを閉じること、フォローアップノートを扱う。承認の前のレビューはレビュー、cumin/status/mergingの外での衝突の解消はチェック、受け入れ確認は受け入れで決める。

全体像

実装Issueがマージでたどる状態を示す。灰色の状態は、ほかのカテゴリで決める。

図の元ファイル: overview.puml

overview.puml

マージはAgentを起動しないので、利用制限でAgent起動を止めている間もマージする（利用制限）。

要件

マージに進む

CWK-MERGE-001 マージを始める

cumin/status/reviewingかcumin/status/awaiting-blocker-mergeの実装Issueで、次のすべてが成り立つとき、cuminは状態をcumin/status/mergingに替える。

  • レビューが完了し（レビューのCWK-REVIEW-004）、そのレビューがAPPROVEである

  • 必須チェックが、今の先頭のコミットで完了している（チェックのCWK-CHECK-002）

  • リスクのラベルが、merge_decision_risks（CWK-MERGE-002）に入っていない

  • blocked byのIssueに関するマージの準備ができている（CWK-MERGE-003）

検証

  • test GitHub mockでテスト

CWK-MERGE-002 マージ判断を求める

CWK-MERGE-001の条件のうち、リスクのラベルだけがmerge_decision_risksに入っているとき、cuminは状態をcumin/status/awaiting-merge-decisionに替え、Pull RequestでAssigneeにレビューを頼み、通知する。レビューを頼むのに失敗しても、ログに残すだけで、実装Issueは止めない。

マージ判断を求めるリスクは、対象のリポジトリの.cumin/config.tomlのmerge_decision_risksで決める。初期値はmediumとhighである。.cumin/は保護されたパスなので（チェックのCWK-CHECK-008.1）、Agentはこの設定を変えられない。

検証
  • test GitHub mockでテスト

CWK-MERGE-003 blocked byのIssueに関するマージの準備

cuminは、次のすべてが成り立つときだけ、実装Issueをマージに進める。cumin/risk/lowでも同じである。これを「blocked byのIssueに関するマージの準備ができている」という。

  • blocked byのIssueがすべて閉じている

  • マージ前のblocked byのIssueのブランチから始めた実装Issue（実装のCWK-IMPL-008）では、さらに次の2つも成り立つ

    • Pull Requestのbaseがmainブランチである
    • blocked byのIssueのマージのあとのmainブランチを取り込んでいる（先頭のコミットが、blocked byのIssueを閉じたPull Requestのマージのコミットを含む）
検証

CWK-MERGE-004 blocked byのIssueを待つ

cumin/status/reviewingの実装Issueで、CWK-MERGE-001かCWK-MERGE-002の条件のうち、CWK-MERGE-003のほかが成り立ち、baseがmainブランチでないか、開いているblocked byのIssueがあるとき、cuminは状態をcumin/status/awaiting-blocker-mergeに替える。この状態では、誰も作業しない。

検証
  • test GitHub mockとCLI mockでテスト

Assigneeによるマージ判断

cuminがマージ判断に使うのは、実装Issueの今のAssigneeのレビューのうち、COMMENTを除いた最新のものだけである（権限のCWK-ACCESS-012）。古いコミットへのレビューは使わない。

CWK-MERGE-005 Assigneeの承認でマージを始める

cumin/status/awaiting-merge-decisionの実装Issueで、Assigneeの最新のレビューが今の先頭のコミットへのAPPROVEで、必須チェックが完了していて、blocked byのIssueに関するマージの準備ができている（CWK-MERGE-003）とき、cuminは状態をcumin/status/mergingに替える。

検証
  • test GitHub mockでテスト

CWK-MERGE-006 Assigneeの指摘を修正する

cumin/status/awaiting-merge-decisionの実装Issueで、Assigneeの最新のレビューが今の先頭のコミットへのREQUEST_CHANGESで、実装Issueが最後にcumin/status/awaiting-merge-decisionになったあとに出たものであるとき、cuminは状態をcumin/status/implementingに替えて、Implementerの直前のセッションで修正を頼む。

  • 修正のあとは、必須チェックとレビューを経て、もう一度CWK-MERGE-002に進む

  • この修正は、レビューのラウンドにもチェックの修正の回数にも含めない。REQUEST_CHANGESを出すのは毎回Assigneeなので、往復が止まらなくなることはない。

検証

  • test GitHub mockとCLI mockでテスト

CWK-MERGE-007 判定の順番

cumin/status/awaiting-merge-decisionの実装Issueでは、CWK-MERGE-005、CWK-MERGE-006、衝突の解消（チェックのCWK-CHECK-007）の順に判定し、最初に成り立ったものだけを行う。衝突していても、Assigneeの判断を先に進める。

マージ

CWK-MERGE-008 GitHub上のマージ前の最終確認

cuminは、cumin/status/mergingの実装IssueのPull Requestを、次のすべてが成り立つときだけマージする。GitHub上でマージ処理するたびに確かめ直す。

  • 必須チェックが、今の先頭のコミットで完了している

  • リスクのラベルが1つだけ付いている

  • Reviewerの最新のレビューが、今の先頭のコミットへのAPPROVEである

  • リスクのラベルがmerge_decision_risks（CWK-MERGE-002）に入っていれば、Assigneeの最新のレビューも、今の先頭のコミットへのAPPROVEである

  • blocked byのIssueに関するマージの準備ができている（CWK-MERGE-003）

検証

  • test GitHub mockでテスト

CWK-MERGE-009 GitHub上でマージ処理する

cumin/status/mergingの実装Issueで、Pull Requestがマージされておらず、CWK-MERGE-008の条件が成り立ち、衝突していないとき、cuminはGitHub上でマージ処理する。

  • マージの方法は、設定merge_method（初期値はsquash）に従う

  • 承認されたコミットだけをマージする。承認のあとにpushされたコミットは、マージしない。

  • 答えが届かなかったときは、次の定期確認で、マージ済みかを読んでから決める。同じPull Requestを、GitHub上で2回マージ処理しない。

  • 1回の定期確認で2つ以上マージするときは、1つごとに数秒待つ

CWK-MERGE-010 チェックに戻る

cumin/status/mergingの実装Issueで、Pull Requestがマージされておらず、CWK-MERGE-008の条件が成り立たないとき、cuminは状態をcumin/status/checkingに替える。どの条件が成り立たなくなっても、checkingから確かめ直せば、チェック、レビュー、マージ判断の要件が、それぞれの原因に合わせて進めるためである。

検証
  • test GitHub mockでテスト

CWK-MERGE-011 マージの前の衝突を解消する

cumin/status/mergingの実装Issueで、CWK-MERGE-008の条件が成り立ち、GitHubが衝突していると返したとき、または衝突でマージを断ったとき、cuminはGitHub上でマージ処理せずに、状態をcumin/status/implementingに替えて、Implementerの直前のセッションで衝突の解消を頼む。チェックの修正の回数には含めない。

検証
  • test GitHub mockとCLI mockでテスト

CWK-MERGE-012 mainブランチが変わってマージを断られたとき

GitHubが、mainブランチが変わったことを理由にマージを断ったとき（405、Base branch was modified）、cuminはcumin/status/mergingのまま、次の定期確認でもう一度GitHub上でマージ処理する。ほかのマージの直後に起きる、すぐに直る断り方だからである。

検証
  • test GitHub mockでテスト

CWK-MERGE-013 マージを止める

cumin/status/mergingの実装Issueで、次のどちらかが起きたとき、cuminは状態をcumin/status/awaiting-decisionに替えて、通知する。

  • GitHubが、衝突でもmainブランチの変更でもない理由で、マージを断った

  • マージのあとで、実装Issueを閉じられない

検証

  • test GitHub mockでテスト

実装Issueを閉じる

CWK-MERGE-014 マージした実装Issueを閉じる

cumin/status/mergingの実装Issueで、Pull Requestがマージ済みになったとき、GitHubが実装Issueを閉じていなければ、cuminが閉じる。cuminが実装Issueを閉じるのは、このときだけである。そのため、Maintainerが開き直した実装Issueは開いたままになる。

検証
  • test GitHub mockでテスト

CWK-MERGE-015 人がマージしたとき

mainブランチのrulesetを迂回できるMaintainerは、Pull Requestを自分でマージしてもよい。そのあとは、cuminがマージしたときと同じに扱う。GitHubが実装Issueを閉じなければ、そのMaintainerが閉じる。

検証
  • test GitHub mockでテスト

フォローアップノート

マージでPull Requestに埋もれる残りの作業を、cuminが要求Issueに書き写す。受け入れ確認で、Plannerがそれを扱う（受け入れ）。

CWK-MERGE-016 フォローアップノートを書く

実装Issueが閉じ、それを閉じるPull Requestがマージ済みで、そのPull Requestのフォローアップノートがまだないとき、cuminは要求Issueにフォローアップノートを1つ書く。誰が閉じたかは問わない。状態は替えない。形式はfollow-up-note.mdに従う。

検証
  • test GitHub mockでテスト

CWK-MERGE-017 フォローアップノートに書くもの

cuminは、次のものを決まった形式から機械的に拾う。何もなければ、ないことを1行で書く。

  • Pull Requestの説明のFollow-upの文章。そのまま写す

  • Reviewerの提案のうち、Implementerの返答がFixedでないもの（レビューのCWK-REVIEW-020）

  • 元からある問題（レビューのCWK-REVIEW-013）

フォローアップノートは、1つのPull Requestに1つだけ書く。あるかどうかは、コメントの目印でGitHubから読む。
