マージ

Reviewerが承認したPull Requestをマージし、実装Issueを閉じるまでの流れを決める。マージ判断、マージ、実装Issueを閉じること、フォローアップノートを扱う。承認の前のレビューはレビュー、cumin/status/mergingの外での衝突の解消はチェック、受け入れ確認は受け入れで決める。

全体像

実装Issueがマージでたどる状態を示す。灰色の状態は、ほかのカテゴリで決める。

図の元ファイル: overview.puml

overview.puml

「Reviewerが動いていない」の意味は、AgentのCWK-AGENT-001で決める。

マージはAgentを起動しないので、利用制限でAgent起動を止めている間もマージする（利用制限）。

要件

マージに進む

CWK-MERGE-001 マージを始める

cumin/status/reviewingの実装Issueで、Reviewerが動いておらず、次のすべてが成り立つとき、cuminは状態をcumin/status/mergingに替える。

  • Reviewerの最新のレビューが、今の先頭のコミットへのAPPROVEである

  • 必須チェックが、今の先頭のコミットで完了している（チェックのCWK-CHECK-002）

  • リスクのラベルがcumin/risk/lowである

  • blocked byのIssueを待たなくてよい（CWK-MERGE-022）

  • 検証: test 4つが成り立つと、実装Issueがcumin/status/mergingになる

CWK-MERGE-002 マージ判断を求める

CWK-MERGE-001の条件のうち、リスクのラベルだけがcumin/risk/mediumかcumin/risk/highのとき、cuminは状態をcumin/status/awaiting-merge-decisionに替え、Pull RequestでAssigneeにレビューを頼み、通知する。レビューを頼むのに失敗しても、ログに残すだけで、実装Issueは止めない。

  • 検証: test cumin/risk/mediumの実装IssueでReviewerが承認すると、cumin/status/awaiting-merge-decisionになり、レビューの依頼と通知が1回ずつ起きる
  • 検証: test レビューの依頼が失敗しても、cumin/status/awaiting-decisionにならない

マージ判断

cuminがマージ判断に使うのは、実装Issueの今のAssigneeのレビューのうち、COMMENTを除いた最新のものだけである（権限のCWK-ACCESS-002）。古いコミットへのレビューは使わない。

CWK-MERGE-003 Assigneeの承認でマージを始める

cumin/status/awaiting-merge-decisionの実装Issueで、Assigneeの最新のレビューが今の先頭のコミットへのAPPROVEで、必須チェックが完了していて、blocked byのIssueを待たなくてよい（CWK-MERGE-022）とき、cuminは状態をcumin/status/mergingに替える。

  • 検証: test Assigneeが今の先頭のコミットを承認すると、cumin/status/mergingになる
  • 検証: test 古いコミットへの承認、ほかのMaintainerの承認、botの承認、あとのREQUEST_CHANGESで覆された承認では、cumin/status/mergingにならない

CWK-MERGE-004 Assigneeの指摘を修正する

cumin/status/awaiting-merge-decisionの実装Issueで、Assigneeの最新のレビューが今の先頭のコミットへのREQUEST_CHANGESで、実装Issueが最後にcumin/status/awaiting-merge-decisionになったあとに出たものであるとき、cuminは状態をcumin/status/implementingに替えて、Implementerの直前のセッションで修正を頼む。

  • 修正のあとは、必須チェックとレビューを経て、もう一度CWK-MERGE-002に進む

  • この修正は、レビューのラウンドにもチェックの修正の回数にも含めない。REQUEST_CHANGESを出すのは毎回Assigneeなので、往復が止まらなくなることはない。

  • 1つのREQUEST_CHANGESで頼むのは1回だけである。Implementerがコミットせずに答えたときは、Assigneeがもう一度判断する。

  • 検証: test REQUEST_CHANGESを出すと、cumin/status/implementingになり、直前のセッションでAgent起動が1回起きる。ラウンドとチェックの修正の回数は変わらない

  • 検証: test Implementerがコミットせずに答えたあと、同じREQUEST_CHANGESで2回目の修正は頼まない

CWK-MERGE-005 判定の順番

cumin/status/awaiting-merge-decisionの実装Issueでは、CWK-MERGE-003、CWK-MERGE-004、衝突の解消（チェックのCWK-CHECK-007）の順に判定し、最初に成り立ったものだけを行う。衝突していても、Assigneeの判断を先に進める。

  • 検証: test 衝突していて、Assigneeが承認した実装Issueは、cumin/status/mergingになる

マージ

CWK-MERGE-006 マージの条件

cuminは、cumin/status/mergingの実装IssueのPull Requestを、次のすべてが成り立つときだけマージする。マージを送るたびに確かめ直す。

  • 必須チェックが、今の先頭のコミットで完了している

  • リスクのラベルが1つだけ付いている

  • Reviewerの最新のレビューが、今の先頭のコミットへのAPPROVEである

  • リスクがcumin/risk/mediumかcumin/risk/highなら、Assigneeの最新のレビューも、今の先頭のコミットへのAPPROVEである

  • Pull Requestのbaseがmainブランチで、blocked byのIssueがすべて閉じている（CWK-MERGE-022）

  • 検証: test cumin/status/mergingを手で付けた、Assigneeの承認のないcumin/risk/mediumの実装Issueは、マージしない

CWK-MERGE-007 マージを送る

cumin/status/mergingの実装Issueで、Pull Requestがマージされておらず、マージの条件が成り立ち、衝突していないとき、cuminはマージを送る。

  • マージの方法は、設定merge_method（初期値はsquash）に従う

  • 承認されたコミットだけをマージする。承認のあとにpushされたコミットは、マージしない。

  • 答えが届かなかったときは、次の定期確認で、マージ済みかを読んでから決める。同じマージを2回送らない。

  • 1回の定期確認で2つ以上マージするときは、1つごとに数秒待つ

  • 検証: test 答えが届かなかったマージで、次の定期確認がマージ済みと読むと、送り直さずに実装Issueを閉じる

  • 検証: test 承認のあとにpushされたコミットは、マージされない

CWK-MERGE-008 チェックに戻る

cumin/status/mergingの実装Issueで、Pull Requestがマージされておらず、マージの条件が成り立たないとき、cuminは状態をcumin/status/checkingに替える。

  • 検証: test cumin/status/mergingのあとで先頭のコミットが変わると、マージせずにcumin/status/checkingになる

CWK-MERGE-009 マージの前の衝突を解消する

cumin/status/mergingの実装Issueで、マージの条件が成り立ち、GitHubが衝突していると返したとき、または衝突でマージを断ったとき、cuminはマージを送らずに、状態をcumin/status/implementingに替えて、Implementerの直前のセッションで衝突の解消を頼む。チェックの修正の回数には含めない。

  • 検証: test 承認のあとに衝突したPull Requestでは、マージを送らずに、衝突の解消を1回だけ頼む

CWK-MERGE-010 mainブランチが変わってマージを断られたとき

GitHubが、mainブランチが変わったことを理由にマージを断ったとき（405、Base branch was modified）、cuminはcumin/status/mergingのまま、次の定期確認でもう一度マージを送る。ほかのマージの直後に起きる、すぐに直る断り方だからである。

  • 検証: test 405で断られた実装Issueは、次の定期確認でマージされる

CWK-MERGE-011 マージを止める

cumin/status/mergingの実装Issueで、次のどちらかが起きたとき、cuminは状態をcumin/status/awaiting-decisionに替え、理由をコメントに書いて、通知する。

  • GitHubが、衝突でもmainブランチの変更でもない理由で、マージを断った

  • マージのあとで、実装Issueを閉じられない

  • 検証: test ほかの理由でマージを断られると、理由のコメントが付いてcumin/status/awaiting-decisionになり、通知が1回届く

blocked byのIssueを待つ

実装のCWK-IMPL-015で始めた実装IssueのPull Requestは、baseがblocked byのIssueのブランチである。blocked byのIssueのPull Requestがマージされると、GitHubはそのブランチを消し、このPull Requestのbaseをmainブランチに替える。

CWK-MERGE-022 blocked byのIssueより先にマージしない

「blocked byのIssueを待たなくてよい」とは、次のすべてが成り立つことである。

  • Pull Requestのbaseがmainブランチである
  • blocked byのIssueがすべて閉じている
  • 先頭のコミットが、blocked byのIssueを閉じたPull Requestのマージのコミットを含む

cuminは、これが成り立つときだけマージに進む。cumin/risk/lowでも同じである。cumin/status/mergingの中では、初めの2つを確かめる（CWK-MERGE-006）。

  • 検証: test baseがblocked byのIssueのブランチのcumin/risk/lowのPull Requestは、Reviewerが承認してもマージされない
  • 検証: test Maintainerが手でbaseをmainブランチに替えても、blocked byのIssueが開いている間はマージされない

CWK-MERGE-020 blocked byのIssueを待つ

cumin/status/reviewingの実装Issueで、CWK-MERGE-001かCWK-MERGE-002の条件のうちblocked byのIssueを待たなくてよいことのほかが成り立ち、baseがmainブランチでないか、開いているblocked byのIssueがあるとき、cuminは状態をcumin/status/awaiting-blocker-mergeに替える。この状態では、誰も作業しない。

  • 検証: test baseがmainブランチでないPull RequestをReviewerが承認すると、cumin/status/awaiting-blocker-mergeになり、Agent起動もマージも起きない

CWK-MERGE-021 mainブランチを取り込む

実装Issueが次のすべてを満たすとき、cuminは状態をcumin/status/implementingに替えて、Implementerの直前のセッションで、mainブランチを取り込むよう頼む。

  • cumin/status/awaiting-blocker-mergeか、CWK-MERGE-020と同じ条件のcumin/status/reviewingである
  • baseがmainブランチで、blocked byのIssueがすべて閉じている
  • 先頭のコミットが、blocked byのIssueを閉じたPull Requestのマージのコミットを含まない

Implementerは強制pushをしないので、mainブランチをマージするコミットで取り込む。取り込んだあとは、必須チェックとレビューを経る。続きの作業なので、空きは待たない。

  • 検証: test blocked byのIssueのPull Requestがマージされると、直前のセッションでAgent起動が1回起きる。空きがなくても起きる
  • 検証: test マージのコミットをすでに含むブランチでは、取り込みを頼まずにマージに進む

CWK-MERGE-023 blocked byのIssueを待つ実装を止める

CWK-IMPL-015で始めた実装Issueで、Agentが動いておらず、次のどれかが成り立つとき、cuminは状態をcumin/status/awaiting-decisionに替え、理由をコメントに書いて、通知する。

  • blocked byのIssueのPull Requestが、マージされずに閉じた
  • この実装IssueのPull Requestが、マージされずに閉じた
  • cumin/status/awaiting-blocker-mergeで、blocked byのIssueのPull Requestがマージされてから定期確認の間隔を過ぎても、baseがmainブランチにならない
  • mainブランチの取り込みを頼んだあとも、先頭のコミットがマージのコミットを含まない

却下されたblocked byのIssueのコミットはブランチに残るので、Assigneeは、それを除くかPull Requestを閉じてから、cumin/status/readyを付ける。

  • 検証: test blocked byのIssueのPull Requestがマージされずに閉じると、cumin/status/awaiting-decisionになり、通知が1回届く
  • 検証: test 取り込みのあとも先頭のコミットがマージのコミットを含まないと、取り込みを繰り返さずに止まる

実装Issueを閉じる

CWK-MERGE-012 マージした実装Issueを閉じる

cumin/status/mergingの実装Issueで、Pull Requestがマージ済みになったとき、GitHubが実装Issueを閉じていなければ、cuminが閉じる。cuminが実装Issueを閉じるのは、このときだけである。そのため、Maintainerが開き直した実装Issueは開いたままになる。

  • 検証: test GitHubが閉じなかった実装Issueをcuminが1回だけ閉じ、Maintainerが開き直しても、もう閉じない

CWK-MERGE-013 人がマージしたとき

mainブランチのrulesetを迂回できるMaintainerは、Pull Requestを自分でマージしてもよい。そのあとは、cuminがマージしたときと同じに扱う。GitHubが実装Issueを閉じなければ、そのMaintainerが閉じる。

  • 検証: test Maintainerがマージして実装Issueを閉じると、cuminがマージしたときと同じフォローアップノートが付く

フォローアップノート

マージでPull Requestに埋もれる残りの作業を、cuminが要求Issueに書き写す。受け入れ確認で、Plannerがそれを扱う（受け入れ）。

CWK-MERGE-014 フォローアップノートを書く

実装Issueが閉じ、それを閉じるPull Requestがマージ済みで、そのPull Requestのフォローアップノートがまだないとき、cuminは要求Issueにフォローアップノートを1つ書く。誰が閉じたかは問わない。状態は替えない。形式はfollow-up-note.mdに従う。

  • 検証: test Follow-upに文章のあるPull Requestがマージされると、要求Issueにフォローアップノートが1つ付く

CWK-MERGE-015 フォローアップノートに書くもの

cuminは、次のものを決まった形式から機械的に拾う。何もなければ書かない。

  • Pull Requestの説明のFollow-upの文章。そのまま写す

  • Reviewerの提案のうち、Implementerの返答がFixedでないもの（レビューのCWK-REVIEW-021）

  • 元からある問題（レビューのCWK-REVIEW-013）

  • 検証: test Follow-upがNoneで、提案がすべてFixedで、元からある問題がないと、フォローアップノートは付かない

  • 検証: test Deferredの提案と元からある問題が1つずつあると、その2つが載る

CWK-MERGE-016 1つのPull Requestに1つ

フォローアップノートは、1つのPull Requestに1つだけ書く。あるかどうかは、コメントの目印でGitHubから読む。

  • 検証: test cuminを再起動しても、同じフォローアップノートは増えない

CWK-MERGE-017 開いている要求Issueだけに書く

閉じた要求Issueには、フォローアップノートを書かない。

  • 検証: test 閉じた要求Issueのsub-issueのPull Requestがマージされても、書かない

CWK-MERGE-018 受け入れ確認の前にそろえる

sub-issueがすべて閉じたとき、cuminは、フォローアップノートを書き終えてから受け入れ確認を頼む（受け入れ）。

  • 検証: test 最後のsub-issueがマージされた定期確認で、フォローアップノートより先に受け入れ確認のAgent起動が起きない

CWK-MERGE-019 Issueにしない

cuminは、フォローアップノートからIssueを作らない。

  • 検証: test フォローアップノートを書いても、Issueの数が増えない

受け入れテスト

# 場面 期待する結果
1 cumin/risk/lowのPull RequestをReviewerが承認する マージに進み（CWK-MERGE-001）、承認されたコミットがマージされ（CWK-MERGE-007）、実装Issueが閉じ（CWK-MERGE-012）、残りの作業があればフォローアップノートが付く（CWK-MERGE-014）
2 cumin/risk/mediumのPull Requestを、ReviewerとAssigneeが承認する マージ判断を求める通知が届き（CWK-MERGE-002）、Assigneeの承認でマージされる（CWK-MERGE-003）
3 AssigneeがREQUEST_CHANGESを出し、Implementerが直す 直前のセッションで修正を頼み（CWK-MERGE-004）、必須チェックとレビューを経て、もう一度マージ判断を待つ。ラウンドとチェックの修正の回数は増えない
4 承認のあと、ほかのマージで衝突する マージを送らずに衝突の解消を頼み（CWK-MERGE-009）、必須チェックとレビューを経て、もう一度マージに進む
5 同じ定期確認で2つマージし、2つめが405で断られる 1つめのあと数秒待ち（CWK-MERGE-007）、2つめは次の定期確認でマージされる（CWK-MERGE-010）
6 最後のsub-issueのPull Requestがマージされる フォローアップノートが付いてから、受け入れ確認を頼む（CWK-MERGE-018）
7 baseがmainブランチでないPull RequestをReviewerが承認し、そのあとblocked byのIssueのPull Requestがsquashでマージされる cumin/status/awaiting-blocker-mergeで待ち（CWK-MERGE-020）、mainブランチを取り込んで（CWK-MERGE-021）、必須チェックとレビューを経てマージに進む。blocked byのIssueより先にはマージしない（CWK-MERGE-022）
8 blocked byのIssueのPull Requestが、マージされずに閉じる そのブランチから始めた実装Issueが止まり、通知が届く（CWK-MERGE-023）
