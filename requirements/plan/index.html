計画

要求Issueを実装Issueに分けるまでの流れを決める。cuminがPlannerを起動し、計画の結果をGitHubで確かめ、Assigneeの計画結果の確認を待つまでである。受け入れ確認は受け入れ、Agent起動に共通のことはAgentで決める。

全体像

要求Issueが計画でたどる状態を示す。acceptingへの遷移は受け入れのカテゴリで決める。

図の元ファイル: overview.puml

overview.puml

「Plannerが動いていない」の意味は、AgentのCWK-AGENT-001で決める。

要求Issueのcumin/status/readyは、いつも「Plannerが要求Issueを読み直す」という意味である。Maintainerは、要求Issueを書き終えたときと、Plannerの質問に答えたときに付ける。Plannerはすでにあるsub-issueを確かめて、足りない分だけを作る。作るものがなく、sub-issueがすべて閉じていれば、受け入れ確認に進む。

Maintainerは、Plannerを通さずに自分でsub-issueを書いてもよい。このときは、自分を要求IssueのAssigneeにし、sub-issueにだけcumin/status/readyを付ける（CWK-PLAN-008）。

要件

計画のAgent起動

CWK-PLAN-001 計画を始める

cumin/status/readyの付いた要求Issueが次のすべてを満たすとき、cuminは状態をcumin/status/planningに替えてから、新しいセッションでPlannerを起動する。sub-issueがすでにあってもよい。

  • そのcumin/status/readyを、cuminが扱う（権限のCWK-ACCESS-004）

  • blocked byのIssueが、すべて閉じている（CWK-PLAN-002）

  • 空きがある

  • 検証: test 3つを満たす要求Issueで、Plannerの起動が1回だけ起き、その前に状態がcumin/status/planningになっている

  • 検証: test どれかを満たさない要求Issueは、cumin/status/readyのまま残る

CWK-PLAN-002 先の要求Issueを待つ

要求Issueが他の要求Issueに依存するときは、Maintainerがblocked byを張る。cuminは、先の要求Issueが閉じるまで、後の要求Issueの計画を始めない。先の成果がまだないmainブランチで計画しないためである。

  • 検証: test blocked byの要求Issueが閉じたあとの定期確認で、計画が始まる

CWK-PLAN-003 実行の時間の上限を渡す

cuminは、Plannerに渡す事実に、ImplementerとReviewerの時間の上限を入れる。Plannerは、1つの実装Issueが1回の実行に収まるように分ける。

  • 検証: test Plannerに渡す事実に、ImplementerとReviewerの時間の上限がある

計画の完了判断

CWK-PLAN-004 計画の完了を判断する

cuminは、Plannerが動いていないとき、要求Issueにsub-issueが1つ以上あり、そのすべてにリスクのラベルが1つだけ付いていれば、計画が完了したと判断する。Plannerのdoneとblockedは使わない。

  • 検証: test sub-issueがないか、リスクのラベルが0個か2個以上のsub-issueがあると、Plannerがdoneを返しても完了と判断しない

CWK-PLAN-005 計画結果の確認を求める

cumin/status/planningの要求Issueで、Plannerが動いておらず、計画が完了し、開いているsub-issueがあるとき、cuminは状態をcumin/status/awaiting-plan-reviewに替えて、通知する。

  • 検証: test 計画が完了するとcumin/status/awaiting-plan-reviewになり、通知は1回だけである

CWK-PLAN-006 計画をやり直す

cumin/status/planningの要求Issueで、Plannerが動いておらず、計画が完了しておらず、Plannerの質問のコメントもないとき、cuminは状態を替えずにPlannerをもう一度起動する。やり直しは、1つのcumin/status/planningの間に1回だけである。

  • 検証: test 計画が完了しないと、Plannerがもう一度だけ起動され、状態はcumin/status/planningのままである

CWK-PLAN-007 計画を止める

cumin/status/planningの要求Issueで、Plannerが動いておらず、次のどちらかが成り立つとき、cuminは状態をcumin/status/awaiting-decisionに替えて、通知する。質問のコメントがないときは、止めた理由をコメントに書く。

  • cumin/status/planningになったあとに、Plannerの質問のコメントがある

  • やり直しのあとも、計画が完了していない

  • 検証: test Plannerがblockedを返すと、やり直さずにcumin/status/awaiting-decisionになる

  • 検証: test やり直しのあとも完了しないと、理由のコメントが付いてcumin/status/awaiting-decisionになる

計画結果の確認

CWK-PLAN-008 実装を始めた印を付ける

要求IssueのAssigneeがsub-issueのどれかにcumin/status/readyを付けたとき、cuminは要求Issueをcumin/status/implementingに替える。替えるのは、要求Issueがawaiting-plan-review、awaiting-acceptance、状態ラベルなしのどれかのときだけである。

  • 要求Issueに状態ラベルがあるときは、要求Issueが今の状態になったあとに付いたcumin/status/readyだけを使う。前の計画のcumin/status/readyが残っていても、新しいsub-issueを確かめる前に進まないためである。

  • 要求IssueにAssigneeがいなければ、進めずに、通知を1回だけ送る。Plannerを通さない要求Issueでは、cuminがAssigneeを付ける機会（CWK-ACCESS-006）がないからである。

  • 検証: test Assigneeがsub-issueにcumin/status/readyを付けると、要求Issueがcumin/status/implementingになり、Agent起動は起きない

  • 検証: test Assigneeのいない要求Issueでは状態が替わらず、通知は1回だけである

  • 検証: test 計画のやり直しでsub-issueが増えた要求Issueは、Assigneeが新しくcumin/status/readyを付けるまでcumin/status/awaiting-plan-reviewのままである

CWK-PLAN-009 残りのsub-issueの確認を求める

cumin/status/implementingの要求Issueで、開いているsub-issueがあり、そのすべてに状態ラベルがないとき、cuminは状態をcumin/status/awaiting-plan-reviewに替えて、通知する。Assigneeが一部のsub-issueにだけcumin/status/readyを付けたとき、要求Issueが黙って止まらないためである。

  • 検証: test cumin/status/readyを付けたsub-issueがすべて閉じ、状態ラベルのないsub-issueだけが残ると、cumin/status/awaiting-plan-reviewになり、通知は1回だけである

Plannerの成果物

CWK-PLAN-010 実装Issue

Plannerは、要求Issueを実装Issueに分け、要求Issueのsub-issueとして作る。1つの実装Issueが、1つのPull Requestになる。本文はimplementation-issue.mdの節で書く。

  • 検証: demo 計画すると、実装Issueがsub-issueとして作られ、どの本文もテンプレートの節を持つ

CWK-PLAN-011 実装Issueの大きさ

実装Issueは、どれも実装Issueの大きさの基準を満たし、合わせると要求Issueの範囲をすべて覆う。

  • 検証: inspection 計画結果の確認で、Assigneeが基準と範囲を確かめる

CWK-PLAN-012 実装の方法を決めてから分ける

Plannerは、コードと外部の文書を調べ、どの実装Issueもそのまま実装できることを確かめてから分ける。調べるだけで決められないときは、Agent作業ディレクトリで小さく試してよい。試しのコードは残さず、結果を計画の全体像のコメントに書く。あとで決まる設計を条件にした実装Issueは作らない。設計文書を書く実装Issueも、その中身は計画で決める。決められないときは、CWK-PLAN-021.3で止まる。

  • 検証: demo 設計の判断が要る要求Issueで計画すると、どの実装Issueにも、設計の結果を条件にした範囲や完了の条件がない
  • 検証: demo 外部のAPIを試さないと決められない要求Issueで計画すると、全体像のコメントに試した結果があり、リポジトリには図のほかに何も足されていない

CWK-PLAN-013 依存関係

Plannerは、実装Issueどうしの依存をblocked byで記録する。blocked byは同じ要求Issueのsub-issueの間だけに張り、循環させない。

  • 検証: demo 順番のある変更を含む要求Issueで計画すると、sub-issueの間にblocked byが張られ、他の要求IssueのIssueには張られない

CWK-PLAN-014 リスクを仮に付ける

Plannerは、実装Issueごとにリスクのラベルを1つだけ付ける。基準は、Plannerが受け取るリスクの基準である（CWK-AGENT-006）。迷ったら高いほうを付ける。cumin/risk/highに当たる変更は、それだけの最小の実装Issueに分ける。

  • 検証: demo データベースのマイグレーションを含む要求Issueで計画すると、マイグレーションだけの実装Issueにcumin/risk/highが付く

CWK-PLAN-015 マイルストーンを写す

要求Issueにマイルストーンがあれば、Plannerは実装Issueに同じマイルストーンを付ける。

  • 検証: demo マイルストーンの付いた要求Issueで計画すると、どの実装Issueにも同じマイルストーンが付く

CWK-PLAN-016 Assigneeが手で行う作業

Implementerが変えられないファイルの変更が要るときは、Plannerはそれを、cumin/type/owner-taskとcumin/risk/highを付けた、状態ラベルのないsub-issueにする。ContextにAssigneeが行う理由を書き、依存する実装Issueにblocked byを張り、計画の全体像のコメントのPlease checkに書く。

  • 検証: demo 保護されたパスの変更を含む要求Issueで計画すると、その変更がこの形のsub-issueになる

CWK-PLAN-017 計画の全体像のコメント

Plannerは、要求Issueに、計画の全体像のコメントを1つ書く。形式はplan-summary.mdに従う。

  • 検証: demo 計画のあとで、要求Issueに全体像のコメントが1つだけある

CWK-PLAN-018 実装Issueの図

Plannerは、どの実装Issueの「Where this fits」にも、変える箇所に色を付けたSVGの図を入れる。ラベルは英語で書く。図はブランチcumin/diagramsのissue-<要求Issueの番号>/に新しいファイルとして足し、コミットを指定して示す。Plannerがリポジトリに書くのは、この図だけである。

  • 検証: demo 計画のあとで、どの実装Issueにも、コミットを指定したcumin/diagramsのSVGがあり、対象の箇所が色で分かる

CWK-PLAN-019 二重に作らない

Plannerは、すでにあるsub-issueを確かめてから作り、同じ実装Issueを二重に作らない。

  • 検証: demo 途中で止めた計画をもう一度させても、同じ実装Issueが二重に作られない

CWK-PLAN-020 要求Issueを変えない

Plannerは、要求Issueの本文を書き換えず、書かれていないことを実装Issueに足さない。要ると考えたことは、要求Issueへのコメントで提案する。

  • 検証: demo 計画のあとで、要求Issueの本文が変わっていない

Plannerが判断を求めるとき

CWK-PLAN-021 推測で計画しない

Plannerは、次のどれかに当たったら、推測で計画せずにblockedを返す。止める理由は、cuminが要求Issueのコメントに書く（CWK-AGENT-013）。

CWK-PLAN-021.1 曖昧な要求

要求が曖昧で、実装Issueの完了の条件を書けないときは、止まる。理由には、何が決まっていないかを書く。

  • 検証: demo 曖昧な要求Issueで計画すると、実装Issueは作られず、決まっていないことが理由に書いてある
CWK-PLAN-021.2 食い違う要求

要求の中に食い違いがあるときは、止まる。理由には、どこが食い違うかを書く。

  • 検証: demo 食い違う2つの決まりを持つ要求Issueで計画すると、実装Issueは作られず、結果はblockedである
CWK-PLAN-021.3 いくつもの設計案

意味のある設計案が複数あり、どれを選ぶかで計画が変わるときは、止まる。理由には、選択肢と得失を書く。

  • 検証: demo 設計案が2つに分かれる要求Issueで計画すると、2つの案と得失が理由に書いてある
CWK-PLAN-021.4 大きすぎる要求

実装Issueの見込みが要求Issueの大きさの基準の上限を超えるときは、止まる。理由には、要求Issueの分け方の案を書く。

  • 検証: demo 上限を超える見込みの要求Issueで計画すると、実装Issueは作られず、分け方の案が理由に書いてある
