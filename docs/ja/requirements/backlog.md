### 既存のコードの定期的なレビュー

Pull Request とは別に、Reviewer が main ブランチの既存のコードを定期的にレビューし、元からある不具合を、ほかの場所で表に出る前に見つける。

- 後回しにした理由: 今は Pull Request ごとのレビューを固めるのが先で、定期的に動く Agent の仕組みもまだない
- 見直すきっかけ: 元からある問題 (`CWK-REVIEW-013`) がフォローアップノートに多く集まったとき

---

### レビューの指標

何ラウンドで通ったか、指摘が直されたか、誤りだったか、意図どおりだったかを集めて、Reviewer の指摘の質とラウンドの数を測る。指摘への返答の3つの分け方 (`CWK-REVIEW-021`) が、その材料になる。

- 後回しにした理由: 測った結果を使って Reviewer の指示を直す流れが、まだ決まっていない
- 見直すきっかけ: ラウンドの上限で止まる実装Issueが目立つようになったとき

---

### よく出る指摘を元で直す

同じ種類の指摘が何度も出るときは、その原因を、skill、lint のルール、Agent が受け取る指示のどれかで直し、次からは指摘が出ないようにする。

- 後回しにした理由: よく出る指摘を見つけるには、レビューの指標が先に要る
- 見直すきっかけ: レビューの指標を集め始めたとき

---
