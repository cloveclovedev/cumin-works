### 既存のコードの定期的なレビュー

Pull Request とは別に、Reviewer が main ブランチの既存のコードを定期的にレビューし、元からある不具合を、ほかの場所で表に出る前に見つける。

- 後回しにした理由: 今は Pull Request ごとのレビューを固めるのが先で、定期的に動く Agent の仕組みもまだない
- 見直すきっかけ: 元からある問題 (`CWK-REVIEW-013`) がフォローアップノートに多く集まったとき

---

### レビューの指標

何ラウンドで承認されたか、指摘が直されたか、誤りだったか、意図どおりだったかを集めて、Reviewer の指摘の質とラウンドの数を測る。指摘への返答の3つの分け方 (`CWK-REVIEW-021`) が、その材料になる。

- 後回しにした理由: 測った結果を使って Reviewer の指示を直す流れが、まだ決まっていない
- 見直すきっかけ: ラウンドの上限で止まる実装Issueが目立つようになったとき

---

### よく出る指摘を元で直す

同じ種類の指摘が何度も出るときは、その原因を、skill、lint のルール、Agent が受け取る指示のどれかで直し、次からは指摘が出ないようにする。

- 後回しにした理由: よく出る指摘を見つけるには、レビューの指標が先に要る
- 見直すきっかけ: レビューの指標を集め始めたとき

---

### マージ判断を待つ Pull Request のブランチから始める深さを選べる

`.cumin/config.toml` の設定で、マージ判断を待つ Pull Request のブランチから始める深さ ([実装](impl/index.md) の `CWK-IMPL-015.1`) を2段以上にできるようにする。そのためには、`cumin/status/awaiting-base` の実装Issueの Pull Request のブランチからも始める条件と、下の段が止まったら上の段も止める決まりが要る。

- 後回しにした理由: 1段でもまだ実際に動かしておらず、2段にしても便利さは大きく変わらない見込みである。深くするほど、下の段が却下されたときに無駄になる実装とレビューが増え、マージのあとの取り込みも段ごとに繰り返す
- 見直すきっかけ: `cumin/status/awaiting-base` の実装Issueに依存する実装Issueが、待たされることが目立ってきたとき
