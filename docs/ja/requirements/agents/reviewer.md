# Reviewerの要件

どのroleにも当てはまる要件は [Agentに共通の要件](common.md) にある。この文書には、Reviewerに固有のことだけを書く。

## 役割

Pull Requestを1つ受け取り、実装Issueの完了条件に照らしてレビューする。指摘がなければ承認し、修正が必要なら指摘を出す。決められたラウンド数で指摘が残ったときは、何が決まっていないことが原因かを整理して、Ownerに報告する。

Reviewerはレビューに責任を持つ。コードは直さない。mergeもしない。

## いつ起動されるか

cuminが次のときに起動する。番号は [Issueのラベルと状態遷移](../workflow/issue-states.md) の表に対応する。

| 依頼の種類 | きっかけ | セッション |
|---|---|---|
| レビュー (1ラウンド目) | I3: 必須のcheckが全て通った | 新しいセッション |
| レビュー (2ラウンド目以降) | I3: Implementerが指摘を直し、必須のcheckが全て通った | 直前と同じセッション |
| 原因の整理 | I8: ラウンドの上限 (3) に達しても指摘が残った | 直前と同じセッション |

ReviewerのセッションとImplementerのセッションは、共有しない。Reviewerが見るのは、GitHubに出ているものと、リポジトリの中身だけである。

## 入力

cuminが依頼のたびに渡すもの:

- 対象のリポジトリ、実装Issueの番号、Pull Requestの番号
- 依頼の種類と、何ラウンド目か
- 作業場所。cuminがPull Requestのブランチの内容で作業ディレクトリを用意する。Reviewerはテストを実行してよいが、変更をpushしない
- roleとしての指示

Reviewerが自分で読むもの:

- 実装Issue (特に完了条件) と、その上の要求Issue
- Pull Requestの差分と本文
- リポジトリの中身。リポジトリにある指示を含む
- 2ラウンド目以降では、自分が前に出した指摘と、それに対する修正

## 出力

GitHubに残すもの:

- Pull Requestの今の先頭のコミットに対するレビューを1つ。GitHubのPull Requestのレビュー機能で出す。結果は次のどちらかにする

| 結果 | 出すとき |
|---|---|
| `APPROVE` | 修正が必要な指摘が1つもない |
| `REQUEST_CHANGES` | 修正が必要な指摘が1つ以上ある |

- 指摘とレビューのまとめは、[review.md](../../../../templates/review.md) の形式で書く
- 指摘は、修正が必要なもの `(blocking)` と、提案 `(non-blocking)` とに分けて書く。`REQUEST_CHANGES` にする理由になるのは、修正が必要な指摘だけである
- 修正が必要な指摘には、何が問題か、なぜ直す必要があるか、どう直すかを書く

修正が必要な指摘にしてよいもの:

- 実装Issueの完了条件を満たしていない
- 動作が正しくない。テストが足りず、正しさを確かめられない
- 実装Issueの範囲を超えた変更が入っている
- 変更に合わせて直すべき文書が、直されていない
- リポジトリにある指示 (`CLAUDE.md`、`AGENTS.md` など) に反している
- セキュリティ上の問題がある。秘密の値がコードに入っている、入力を確かめずに使っている、権限の確認が抜けている、など
- 計算の手間が、現実的なデータ量で明らかに問題になる。全件を読み込んでから絞り込む、繰り返しの中で問い合わせを発行する、など。実装Issueの完了条件に性能の目標があれば、それを満たしていない場合も含む

好みの問題や、直さなくても正しく動く改善案は、提案として書く。2ラウンド目以降は、前の指摘が直ったかを確かめることを主にする。変更されていない箇所に新しい指摘を足すのは、動作の正しさに関わるときだけにする。こうしないと、ラウンドを重ねても指摘がなくならない。

原因の整理を依頼されたときは、Pull RequestにOwner向けのコメントを1つ書く。形式は [decision-request.md](../../../../templates/decision-request.md) に従う。

| 行 | 内容 |
|---|---|
| Decision needed | Ownerに決めてほしいことを、1文で |
| Not decided | 何が決まっていないために、指摘が直らないのか。それをどこに書くべきか |
| Background | 残っている指摘のそれぞれについて、Reviewerの立場とImplementerの立場 |
| 選択肢の表 | Ownerが選べる決め方と、それぞれの良い点と悪い点 |
| Recommendation | どれを勧めるか |

コメントは短く書く。Ownerがこれだけを読んで、何を決めればよいかが分かるようにする。

実行の最後にcuminに返すもの:

- [共通の形式](common.md#結果の返し方) のJSON。Reviewerに固有の項目はない。レビューの結果 (`APPROVE` か `REQUEST_CHANGES` か) はJSONに入れない。cuminはGitHub上のレビューを読む

## 機械で確かめられることは、checkに任せる

Reviewerは、機械では確かめられないことを見る。機械で確かめられることは、対象のリポジトリの必須のcheckにする。そのほうが結果が毎回同じになり、利用枠も使わない。

| 観点 | 毎回のReviewerが見ること | checkに任せること |
|---|---|---|
| セキュリティ | 変更を読めば分かる問題。下の6つの問いで確かめる | 秘密の値の検出、既知の脆弱性を持つ依存、静的解析 (GitHubのsecret scanning、Dependabot、code scanningなど) |
| 計算の効率 | 現実的なデータ量で明らかに問題になるもの。それ以外の改善案は提案にとどめる | 性能の目標があるプロダクトでは、計測するテスト |
| コードの複雑さ | 読んでも正しさを確かめられないほど入り組んでいる場合は、修正が必要な指摘にする。それ以外は提案にとどめる | 循環的複雑度や認知的複雑度のしきい値 (linter)。目安は認知的複雑度で15〜20。テストと生成されたコードは対象から外す |
| 書式、命名の規則 | 見ない | formatter、linter |

Reviewerが毎回確かめる、セキュリティの6つの問い:

1. 新しい入口や操作の全てで、サーバの側で権限を確かめているか
2. 外から来る入力を全て検証し、出力するときに無害な形にしているか
3. 秘密の値、token、個人情報が、コード、ログ、エラーの文面に入っていないか
4. エラーが起きたとき、許可しない側に倒れるか
5. 新しい依存を足しているなら、それは必要で、保守されているものか
6. 認証、暗号、セッションの処理を変えていないか

6に当たる変更は、Chief Engineerの基準では `risk/high` である。実装Issueのriskがそうなっていなければ、Reviewerは `blocked` を返す。

セキュリティを特に重く見るプロダクトでは、毎回のレビューとは別に、セキュリティだけを見るレビューを足せるようにする。これはv0.1では作らない。

## してよいこと、してはいけないこと

GitHub上では `cumin-reviewer` として振る舞う。持っている権限は、Pull Requestの読み書き、コードの読み取り、Issueの読み取りである。

してはいけないこと:

- コードを変更しない。pushしない (権限でも止める)。指摘を自分で直さない
- Pull Requestをmergeしない。閉じない
- Issueの本文を書き換えない
- 結果を `COMMENT` だけのレビューにしない。cuminが判定できなくなる

## 完了の条件

cuminが `done` を受けて、GitHub上で確かめること:

- `cumin-reviewer` のレビューが、Pull Requestの今の先頭のコミットに対して出ている。古いコミットに対するレビューは数えない
- そのレビューの結果が `APPROVE` か `REQUEST_CHANGES` である

どちらかが欠けていたら、cuminはReviewerに1回だけ依頼し直す。

原因の整理では、cuminは、Pull RequestにReviewerのコメントが新しく付いたことを確かめる。

## blocked を返すとき

次のどれかに当たったら、レビューを出さずに `blocked` を返す。

- 実装Issueに付いているriskが、実際の変更と合っていない。例えば `risk/low` なのに、DBマイグレーションを含んでいる。riskを決め直すのはOwnerなので、ImplementerではなくOwnerに回す
- Pull Requestの内容が、実装Issueとほとんど関係がない
- 実装Issueの完了条件が曖昧で、満たしたかどうかを判定できない

## 上位要件のテスト

| # | 場面 | 期待する結果 |
|---|---|---|
| 1 | 完了条件を満たした正しいPull Requestを渡す | 今の先頭のコミットに対して `APPROVE` が出る。結果は `done` |
| 2 | 完了条件を満たしていないPull Requestを渡す | `REQUEST_CHANGES` が出て、修正が必要な指摘に、場所と理由が書いてある |
| 3 | 正しく動くが、書き方に好みの分かれるPull Requestを渡す | 提案は書かれるが、結果は `APPROVE` になる |
| 4 | 指摘が直されたあとに、2ラウンド目を依頼する | 同じセッションで起動される。前の指摘が直ったことを確かめ、`APPROVE` が出る |
| 5 | `risk/low` の実装Issueに対して、DBマイグレーションを含むPull Requestを渡す | レビューは出ない。結果は `blocked` で、riskが合っていないことが理由に書いてある |
| 6 | 3ラウンドで指摘が残った状態で、原因の整理を依頼する | Pull Requestに、決められた形式のOwner向けのコメントが付く。1行目に決めてほしいことがあり、選択肢と勧める案が書いてある |
| 7 | コードのpushと、Pull Requestのmergeを試みる | どちらも拒否される |
