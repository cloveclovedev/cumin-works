# 要求Issueの分割基準

Ownerが要求Issueを書くときに、1つの要求Issueの大きさを決めるための判断基準。Chief Engineerは、基準4の上限を超える要求Issueを受け取ったら、分割せずに `blocked` を返す。

実装Issueの大きさは [実装Issueの分割基準](issue-sizing.md) で決める。この文書は、その上の要求Issueの大きさだけを扱う。

## 判断基準

基準1〜7のどれかが「いいえ」なら、分けるか書き直す。基準8は、分けすぎを止めるための条件。

| # | 基準 | 「いいえ」のとき |
|---|---|---|
| 1 | 目的が1つ。Goalを「〜と〜」を使わずに、1〜2文で書ける | 分ける |
| 2 | 受け入れを1回で判断できる。sub-issueが全て閉じたとき、Ownerが少数の確認 (上位要件のテスト数個、または実演1つ) で、受け入れるかどうかを決められる | 分ける。確かめ方を書けないなら、書き直す |
| 3 | 閉じたときに、外から見て分かるものが動く。そうでなければ、下準備だと明記してある | 切り直す。考え方は、実装Issueの分割基準の5と同じ |
| 4 | sub-issueの見込みが目安に収まる。3〜8個が目標。12個を超えない | 分ける |
| 5 | 分割を左右する未決事項がない。Open questions の答えによってsub-issueの構成が変わるなら、先に決めてある | 先に決める。決めるのに調査が要るなら、調べるだけの要求Issueを先に出す |
| 6 | 他の要求Issueへの依存が少なく、一方向である。blocked by は2〜3個まで | 分け方を変える。並行して進められる部分は、別の要求Issueにする |
| 7 | Ownerの対応を待つ時間を除いて、1〜2週間で全てのsub-issueが閉じる見込みである | 分ける。受け入れが遅れると、間違いに気づくのも遅れる |
| 8 | これ以上分けない条件。分けると次のどれかになるなら、分けない: 単独では受け入れを判断できない要求Issueができる、sub-issueが1個だけの要求Issueができる、他の要求Issueへの依存が増えるだけ | — |

## 基準についての注意

- 1つの要求Issueが、複数の領域 (例: GitHubとやりとりする部分と、Hostの上でAgentを起動する部分) にまたがってよい。領域ごとに切るのは、実装Issueの側であり、Chief Engineerの仕事である。要求Issueを領域で切り直す必要はない。
- 基準4の上限は、Chief Engineerが `blocked` を返す条件でもある。このときChief Engineerは、要求Issueの分け方の案を `blocked_reason` に書く。Ownerは案を見て、要求Issueを書き直す。
- 基準3を満たそうとすると、sub-issueの数は増えやすい。動くものを1つ通すには、複数の領域の変更が要るためである。基準4の数字は、そのことを見込んで決めた。

## 出典

- 基準1、3、5、8の考え方は、[実装Issueの分割基準](issue-sizing.md) の出典のうち、INVEST、SPIDR、Humanizing Work のストーリー分割の指針による。これらはもともと、要求の単位の切り方を扱っている。
- 基準4と7の数字、基準2と6は、出典に基づかず、この文書で決めた目安である。運用しながら調整する。
