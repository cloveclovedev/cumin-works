# cumin-works要求仕様書

cumin-worksは、GitHubのIssueとPull Requestを見ながら、決められたルールだけでAgentを起動し、計画、実装、レビュー、マージまでを進めるツールである。人は要求を書き、要所で判断する。

## 解決したい課題

1. 人が手を動かしていない時間には、Agentもほとんど使われない
2. Agentを使い始めるきっかけが人のやる気と空き時間になっている。人が忙しいほど、Agentも動かない。
3. 時刻で起動するような自動化はできても、それだけではマージされる成果物に結びつく使い方にならない。何を頼み、結果をどう確かめ、次に何をするかを、毎回人が決めている。

## 目的

Maintainerの負担をできるだけ減らしながら、Agentを動かし続け、時間あたりの成果を最大にする。

## 指標

- 稼働: 週間制限の使用率。設定で決めた目標に近いほどよい。稼働は成果そのものではない。Agentが動き続けることを直近の目標にするための暫定の指標である。
- 成果: 週ごとの、マージされた実装Issueの数と、受け入れられた要求Issueの数
- Maintainerの負担: 要求Issue 1つあたりで、その要求Issueとsub-issueがMaintainerの番の状態（`awaiting-`で始まる状態）になった回数。少ないほどよい。

## 登場人物

### 人とAgent

- Maintainer: 対象のリポジトリにwrite以上の権限を持つ人。要求Issueを書き、要求Issue実装開始を判断する。
- Assignee: Issueの指示と判断を受け持つMaintainer。GitHubのIssueのassigneeで表し、1つのIssueに1人。
- Operator: Hostでcuminを動かし、Hostの設定と利用制限を受け持つ
- Agent: cuminが起動するAI。Planner、Implementer、Reviewerの3つのroleがある。
  - Planner: 要求Issueを計画し、マージされた結果の受け入れ確認をする
  - Implementer: 実装Issueを実装し、Pull Requestにまとめる
  - Reviewer: Pull Requestをレビューする

### システム

- cumin: Hostに常駐し、GitHubを定期確認して、状態ラベルを替え、Agent起動とマージを行う
- Host: cuminが動くマシン。macOSを対象にする。
- GitHub: 要求、作業、成果物と、その状態を記録する唯一の場所。cuminと各roleは、それぞれのGitHub AppでGitHubを使う。GitHub Appの名前は運用する組織ごとに決める。

## 原則

### ワークフローの原則

- Agentの判断で要求から外れないように、適切なタイミングでMaintainerに判断を求める
- Maintainerが判断するときの負担を、できるだけ小さくする
  - 変更を1回で判断できる大きさに分ける
  - 判断に必要な情報（変更の内容やスコープ）を、できるだけ図で示す
- 可能な限りAgentを自律的に動かしつつリスクも下げるために、Agentにはその作業に必要な最小の権限だけを渡す。人の認証情報は渡さない。

### cuminの原則

- cuminは決められたルールだけで動く。AIによる判断を含まない。要求の解釈、計画、実装、レビュー、リスクの判断は、すべてAgentかMaintainerが行う。
- 同じGitHubの状態からはいつも同じアクションを決める
- 状態はGitHubに置く。cuminが手元に持つのは、失っても作業を失わないものだけである。
- 完了はGitHubの上の事実で決める。Agentの申告では決めない。

## 範囲外

- WindowsとLinuxでは動かさない

## 進め方

- シンプルファースト: 要件を満たすいちばん単純な方法を探す
- 要件ファースト: すべての振る舞いは要件をたどれる。要件文書は、Maintainerが全体を把握できる大きさに保つ。
- ドキュメントファースト: 文書は常に最新に保たれている
- テストファースト: 細かいユニットテストを多く書くより、受け入れテストで要件を確かめることを優先する

## フェーズ

バージョンごとの目標を書く。期日の目安と、どの要求Issueがどのバージョンに入るかは、GitHubのマイルストーンで管理する。

| バージョン | 目標 |
|---|---|
| v0.1 | peppercheckの作り直しをcumin-worksで進められる |
| v0.2 | 実際に使って分かったことを直し、コードと文書を整理する。新しい機能は足さない |
| v0.3 | 個人のアカウントでセットアップでき、Freeプランのprivateリポジトリでも、限られたワークフローで使える |
| v1.0 | cumin-worksを公開する。peppercheckの作り直しとcumin-works自身の開発が、cuminで問題なく進む |

要件のページにあるのは、今のフェーズまでに作ると決めたことである。あとで取り入れたいことは[バックログ](backlog.md)にある。
