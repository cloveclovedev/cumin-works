# cumin-works 要求仕様書

cumin-works は、GitHub の Issue と Pull Request を見ながら、決められたルールだけで Agent を起動し、計画、実装、レビュー、マージまでを進めるツールである。人は要求を書き、要所で判断する。

## 解決したい課題

1. 人が手を動かしていない時間には、Agent を使える利用制限がほとんど使われずに残る。
2. Agent を使い始めるきっかけが人のやる気と空き時間になっている。人が忙しいほど、Agent も動かない。
3. 時刻で起動するような自動化はできても、それだけではマージされる成果物に結びつく使い方にならない。何を頼み、結果をどう確かめ、次に何をするかを、毎回人が決めている。

## 目的

Maintainer の負担をできるだけ減らしながら、Agent を動かし続け、時間あたりの成果を最大にする。

## 指標

どれも、GitHub と、cumin が読む利用制限の使用率から、週ごとに出せる。

- 稼働: 週の終わりの時点の、週間制限の使用率。設定で決めた目標に近いほどよい。稼働は成果そのものではない。Agent が動き続けることを直近の目標にするための暫定の指標である。
- 成果: 週ごとの、マージされた実装Issueの数と、受け入れられた要求Issueの数。
- Maintainer の負担: 要求Issue 1つあたりで、その要求Issueと sub-issue が Maintainer の番の状態 (`awaiting-` で始まる状態) になった回数。少ないほどよい。

## 登場人物

### 人と Agent

- Maintainer: 対象のリポジトリに write 以上の権限を持つ人。要求Issueを書き、進めてよいと合図する。
- Assignee: その Issue の指示と判断を受け持つ Maintainer。GitHub の Issue の assignee で表し、1つの Issue に1人だけ付ける。
- Operator: Host で cumin を動かし、Host の設定と利用制限を受け持つ。
- Agent: cumin が起動する AI。Planner、Implementer、Reviewer の3つの role がある。
  - Planner: 要求Issueを計画し、マージされた結果の受け入れ確認をする。
  - Implementer: 実装Issueを実装し、Pull Request にまとめる。
  - Reviewer: Pull Request をレビューする。

### システム

- cumin: Host に常駐し、GitHub を定期確認して、状態ラベルを替え、Agent起動とマージを行う。
- Host: cumin が動くマシン。macOS を対象にする。
- GitHub: 要求、作業、成果物と、その状態を記録する唯一の場所。cumin と各 role は、それぞれの GitHub App で GitHub を使う。GitHub App の名前は運用する組織ごとに決める。

## 原則

### ワークフローの原則

- Agent の判断で要求から外れないように、適切なところで Maintainer に判断を求める。
- Maintainer が判断するときの負担を、できるだけ小さくする。
  - 変更を1回で判断できる大きさに分ける。
  - 判断に要る情報 (変更の内容と、全体の中での位置) を、できるだけ図で示す。
- 人が見ていない間も Agent を動かせるように、Agent にはその作業に要る最小の権限だけを渡す。人の認証情報は渡さない。

### cumin の原則

- cumin は決められたルールだけで動く。AI による判断を含まない。要求の解釈、計画、実装、レビュー、リスクの判断は、すべて Agent か Maintainer が行う。
- 同じ GitHub の状態からはいつも同じアクションを決める。
- 状態は GitHub に置く。cumin が手元に持つのは、失っても作業を失わないものだけである。
- 完了は GitHub の上の事実で決める。Agent の申告では決めない。

## 範囲外

- Windows と Linux では動かさない。

## 進め方

- シンプルファースト: 要件を満たすいちばん単純な方法を探す。AI の道具は速く変わる。
- 要件ファースト: すべての振る舞いは要件にたどれる。要件の量は、Maintainer が全体を把握できる大きさに保つ。
- ドキュメントファースト: 文書はいつも、動いているものに追いついている。
- テストファースト: 細かいユニットテストを多く書くより、受け入れテストで要件を確かめることを優先する。

|---|---|
| v0.1 | peppercheck の作り直しを cumin-works で進められる |

| v1.0 | cumin-works を公開する。peppercheck の作り直しと cumin-works 自身の開発が、cumin で問題なく進む |

要件のページにあるのは、今のフェーズまでに作ると決めたことである。あとで取り入れたいことは [バックログ](backlog.md) にある。
